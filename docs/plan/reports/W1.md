### Retrieval pipeline (`memory.retrieve.search`)

1. **Rewrite.** IDs are normalised (`e-1`→`E-1`, `rfi 50`→`RFI-050`, `is 456`→`IS 456`). A follow-up (pronoun, ellipsis, or ≤2 content words) inherits the previous turn's IDs and topic from session memory. LLM rewriting is used only in `ask`, and only when a pronoun is present.
2. **Decomposition** runs only when a regex matches (`and / vs / compare / between / aur`, ≥6 words). The original query is kept alongside the parts.
3. **Parallel legs** run in a thread pool:
   - LanceDB cosine top 30 per sub-query, pre-filtered by `dataset IN (...)`.
   - SQLite FTS5 BM25 top 15, with column weights text 1, title 2, section 1.5, entities 4. Exact-ID phrase and entity-column terms are included, plus a Hinglish→English term map.
4. **Fusion** uses RRF k=60, plus:
   - an exact-entity leg for chunks whose entity column contains every key ID in the question,
   - a thin IS-code stub down-weight of ×0.75,
   - a project-scope boost of ×1.5, with the top 3 project passages guaranteed a place in the rerank head.
5. **Rerank.** The cross-encoder scores the top 10. It reads each chunk's most query-dense window of about 520 chars (not just the start of the chunk). Scores are cached per (query, chunk). Reranking is skipped when an exact-ID BM25 hit dominates.
6. **Selection.** Keep 8 hits, at most 3 per document, with fingerprint dedup. The top 3 get ±1 neighbour chunks as context.
7. **Abstain** when there are no hits, when a key entity (RFI, drawing, grid, code, clause, template, permit, checklist) in the question appears in none of the kept hits, or when the best rerank score is below `MEMORY_ABSTAIN_THRESHOLD`.

Responses carry `timingsMs {rewrite, embed, vector, bm25, fuse, rerank, llm, total}`.

### Scope isolation
- A project call reads exactly `org_<org>__proj_<project>` plus `kb_templates`, `kb_is_codes`, `kb_prices_sor` and `kb_handbook`.
- The org comes from `tenancy.auth.require_project()`, never from the request body.
- Without a `projectId`, only global datasets are searched.
- **A leak I found and fixed.** The 8 site.db "code_clause" notes contain P1 site tolerances. They had been put in the global `kb_is_codes`, which let P1 values show up in other projects. They now live in the P1 dataset.
- **Verified.** The golden set's 3 Nashik cases show no P1 hits. Another org gets 404 on a foreign project. A write to demo P1 gets 403.

### Project profile → prime memory
`ingest_project_profile(org_id, project_id, profile, email=None)` enqueues and returns `{status:"queued", jobId, docId, dataset}` in milliseconds. W2 calls it inside `POST /api/projects`.

The worker turns the flat profile, labelled via `data/onboarding_schema.json`, into short fact-sheet passages:
- an identity summary,
- one passage per onboarding step, at most 5 lines each,
- one explicit line per repeater row, for example: "Structural consultant: Sthapatya Structural Engineers — Dr. V. N. Rao, Phone …".

Re-ingest replaces the previous version (`source_key=project_profile`).

Crawled-section ingest crashed once, on two identical gate pages in one batch (duplicate `chunk_id`). `ingest_docs` now de-duplicates by (dataset, content_hash), and the resumable re-run finished the section.

**ETA for a full rebuild from scratch on this M3:** about 21k chunks at 19–24 chunks/s ≈ **15–18 min** when nothing else is using the GPU or RAM. The run above took about 45 min because two backends and the reranker were swapping.

- **Throughput ceiling.** Embedding is about 100% of index time; LanceDB appends and SQLite/FTS writes are negligible. The ingest already sends Ollama batches of 64 and does one LanceDB append per 600 chunks.
- **Benchmarks on this M3:**
  - Ollama bge-m3 at batch 32/64/128: 23–24 chunks/s. 4 concurrent requests add nothing.
  - sentence-transformers bge-m3 on MPS fp16: 27–30 chunks/s.
  - Parity between the two engines: cos 0.9998 minimum.
  - The switch was not made because 1.25× is well below the ≥5× bar. A later switch would not need a re-embed.
- **Contention.** Under the RAM pressure of two backends each holding a reranker, plus the ingest, plus Ollama, real throughput fell to 5–8 chunks/s. The fix was one backend, `OLLAMA_NUM_PARALLEL=1`, and `OLLAMA_KEEP_ALIVE=30m`.
- **Full global corpus size.** About 21.5k chunks. At a clean 24 chunks/s that is roughly 15 min of embedding; under contention it is 40–60 min.
- **Chunk budget.** The crawler output would have produced 36.6k chunks. Capping thin stubs, grouping clause cards, and keeping full body text only for curated codes brought it to 15.1k for the crawled sections.

| Metric | Value |
|---|---|
| recall@8, answerable (31) | **1.000**: record 10/10, Hinglish 5/5, templates 6/6, IS codes 5/5, prices 2/2, handbook 2/2, Nashik project scope 2/2 |
| answered and found | **1.000** (no false abstains) |
| abstain precision / recall (13 must-abstain) | **1.000 / 1.000** |
| threshold | 0.03 in use. The sweep gives P = R = 1.0 over 0.02–0.04 |
| cross-project scope leaks | **none** |
| search p50 / p95, uncached query | **386 / 514 ms**. rerank 367 / 481, bm25 16 / 97, vector 9.5 / 15, fuse 0.7 / 2.3, embed < 2 (query-embedding disk cache warm from the previous run; about 40 ms uncached) |
| search p50 / p95, repeated query (rerank score cache) | **9.4 / 19.9 ms** |
| ask p50 / p95 (Groq gpt-oss-120b, reasoning low), n=10 | **480 / 2,611 ms** |
| engine regression cases / scenarios | 9/9 · **10/10, wrong logs 0** |

Against the targets:
- **Met:** the non-rerank legs (about 27 ms total), repeated-query search, and ask p50 ≤1.2 s.
- **Not met:** uncached search p50 ≤150 ms. The bge-reranker-v2-m3 cross-encoder costs about 370 ms for 8 pairs on the M3 GPU.
- **Levers:** `MEMORY_RERANK_HEAD=4–6`, a lighter `MEMORY_RERANK_MODEL`, or `rerank_mode="off"` for the voice fast path. With rerank off, abstention would rely on entity checks alone.
- **Reporting:** `timingsMs.rerankMode` (`cross_encoder | cached | skipped_exact_id | off | unavailable`) and `rerank {mode, scored, cached}` explain every `rerank: 0` in a response.

Live site record: for P1, status questions (permits, hold points, RFIs, blockers, pours) get a passage built at query time from site.db by the deterministic engine (citation "per the live site record"), so they never abstain on a stale snapshot. Verified: "Which permits are blocking work today?" and "What should I check before the L4 slab pour?" both answer from it.

Number guard: every number in `answer` and `speech` must appear in the passages the model was given. Sentences that fail are dropped (`droppedUnsupported`), and if none survive the reply is the abstain line. The "20 mm" in the L4 pour answer is in the record: CL-PP-L4-001 B3 "req. 20±5" and S-301 R2 slab cover 20 mm ±5.

## 5. Fix 1: confident wrong answers (`backend/engine/answer.py`)

| Input | Before | After |
|---|---|---|
| "chiller commissioning checklist?" | CL-PP-L3 pre-pour log | FMT-MEP-002 template (the record's FTS hit, relevance-gated) or the memory answer |
| "lap length 16 mm M25?" | asked for a grid (not seen as a question) / RFI-041 | Classed as a question (knowledge cue with no location). Answered by memory, otherwise "That isn't in the project record or the knowledge base." |
| "curing period IS 456?" | L4 hold point | memory answer / KB abstain line |
| "today's steel rate?" | 2026-09-11 site diary | a topic word no longer hijacks the question; memory / abstain |
| "What cover does IS 456 require for columns?" | "which grid line?" | memory: "Columns need at least 40 mm cover…" (3.5 s on /api/turn) |
| "whats the pending blockers" | RFI-049 only | open hold points (CL-PP-L4-001), permit blockers (HWP-0112 checks), open RFIs |
| "Give all information you can for Level 3" | RFI-049 | level summary: permits, hold points, open RFIs, current drawings, fact count |
| "But you said that M-401 is pending, where did RFI-049 come from" | asked for a location | "RFI-049, Plumbing sleeve clash… open… against drawing M-401. Impact: Pending — may affect M-401. So M-401 R1 is flagged because this RFI is still open." |

Mechanics:
- **`is_question`.** A number counts as a question when a knowledge cue is present, no grid, zone or drawing is named, and the utterance is interrogative. Follow-up phrases (where did, come from, you said, explain) also count.
- **Topic answers** are accepted only when every other content word of the question appears in the answer.
- **`_from_memory`** rows must cover every content word.
- **RFI IDs** are explained from the register.
- **A level named without a grid** gets a level summary.
- **Unresolved questions** go to `memory.api.ask`, with an 8 s timeout and `VESPER_MEMORY_ASK=0` to disable. On abstain the reply is NOT_FOUND, or the KB abstain line for knowledge questions, with `unresolved: true`.
- **Unchanged:** contradiction, logging and drawing-fact behaviour. Memory never authorises a log.

## 6. How to run

```bash
ollama pull bge-m3 && OLLAMA_NUM_PARALLEL=1 OLLAMA_KEEP_ALIVE=30m ollama serve   # one embedding engine
backend/.venv/bin/pip install -r backend/requirements.txt
backend/.venv/bin/python scripts/ingest_knowledge.py                      # all (resumable) → data/memory/ingest_log.txt
backend/.venv/bin/python scripts/ingest_knowledge.py --only templates,p1  # just site.db
backend/.venv/bin/python scripts/eval_memory.py --http http://localhost:8000 --ask 8
backend/.venv/bin/python scripts/eval_memory.py --engine && (cd backend && .venv/bin/python scenarios.py)
```
Run only ONE backend process at a time on a 16 GB Mac. Each backend loads the reranker (~1.1 GB fp16), and a second copy pushes the machine into swap.

## 8. Gaps / known issues
1. **Cognee knowledge graph is not running.**
   - cognee 1.5.4 is installed in `backend/.venv-cognee`; it conflicts with the backend venv (openai<3, websockets<16).
   - Its relational schema comes only from Alembic migrations. On macOS those import the Ladybug (Kuzu fork) C-API dylib, which the `ladybug==0.19.0` wheel does not ship ("Could not find lbug C API shared library").
   - With migrations off, no tables exist ("no such table: principals"). The file-based `turso` graph provider does not avoid the problem.
   - The worker, queue, lock, backoff, Cerebras fallback and snapshot export are written. Documents keep `graph_status='pending'` for a later run.
   - **To enable:** provide `LBUG_C_API_LIB_PATH` (Ladybug's `download_lbug.sh`, not run here: no binary downloads), then `MEMORY_COGNEE_ENABLED=1 backend/.venv-cognee/bin/python backend/memory/cognee_worker.py --max-docs 40`.
   - Until then `/api/memory/graph` serves the entity co-mention graph built from the index.
2. **Latency targets.** Uncached-query search p50 is dominated by the cross-encoder (§4), and ingest throughput is GPU-bound at about 24 chunks/s on the M3.
3. **No OCR.** Image uploads return 415.
4. **Voice ingest.** Sarvam REST sync accepts short clips only (about 30 s); longer notes need the batch API. Not exercised with real audio.
5. **Profile field keys (for W2).** The fact sheet renders any flat profile; roles are labelled from schema options.
6. **Re-embedding is not needed** if the embedding engine switches to sentence-transformers (parity 0.9998). A model change of any other kind requires a rebuild (`embedding_version` is stored per chunk).
7. **ANN index.** `store.build_indexes()` creates BITMAP(dataset), BTREE(doc_id) and IVF_HNSW_SQ at the end of a full run. At about 20k vectors a flat scan measured 60–100 ms including the pre-filter.
